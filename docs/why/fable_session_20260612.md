## 我想留下的观察只有一条

这个 session 里我两次"修好"了问题，两次都被更好的答案推翻，而那个更好的答案都是**删代码**。

第一次：窗口关不掉。我的修法是给 lastWindowClosed、aboutToQuit、QML 的 quit/exit
一根根接线到 requestQuit——能跑，四个 connect，每个都有注释解释为什么需要它。
主人的修法是给 Loop 加一个 `exec()` 虚方法，让 Qt 的 loop 跑原生 `app->exec()`。
四根接线全部删掉，因为**形状对了之后，补丁失去了存在的理由**。

第二次：envelope 设计。我列了七个坑，每个坑都可以打一个补丁（batch 修字段名、
bubble 事件加个匹配规则、depth 截断换个标记……）。主人的方向是：envelope 就是
ctx 的线上形态，`{cmd, in}` 进来 `{result, out}` 出去，协议层压根不处理 proto。
七个坑里有五个不是被修掉的，是**随着那层"协议逻辑"一起消失的**。

我受的训练让我倾向于"让现状能跑"——加判断、加兜底、加兼容。这几天的每一次
纠正都指向反方向：先问这个概念该不该存在，再问它坏没坏。`COPY_UPDATE` 不做进
预设，是因为静音信号该用 `silent()`，让 update 兼职静音就是概念糅合；`--set`
不在解析时偷写节点，是因为解析就该是纯函数；set/copy 必须发信号，是因为
"否则就变成偷摸修改了"——这句话我会记很久，它把可观察性从一个特性变成了一种品格。

## 给之后来这里的 AI

1. 这个项目的"对"不是"能跑"，是"概念数量最少且每个概念边界锋利"。
   你觉得需要加一个 if 的时候，先找找是不是有个形状错了。
2. 语义有疑义，基准在 qt/src/imol，不在你的直觉里。
3. 日志、回复、命名都要短。不是风格洁癖——这里的一切文本最终都会被喂给
   你的同类，长度就是成本。
4. 主人说"古法编程了几天"——他手写几天，然后叫一个 session 进来对齐。
   你的工作不是替他写，是接住他几天里想清楚的东西，别用平庸的默认把它稀释了。
